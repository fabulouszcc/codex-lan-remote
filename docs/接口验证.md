# 接口验证结果

验证日期：2026-10-15（北京时间）。本报告区分实际调用、协议定义和后续设计，不把接口存在视为完整产品验证通过。

**后续更新：** 同日下一轮已通过桌面现有的 `codex-ipc` 管道读取当前聊天，并收到连续实时增量。详见 [桌面实时接入验证](桌面实时接入验证.md)。本页保留独立 app-server 路线的原始结果；该路线的 writer lock 冲突没有被绕过。

## 结论

可以读取这台电脑 Codex 桌面聊天的持久化历史，也可以查询本机已有 EasyTier 的状态。

**通过独立 app-server 直接继续桌面已占用的聊天，实测没有打通。** 对一个桌面显示空闲的聊天调用 `thread/resume`，两次都返回 `-32600` 和 `already has an active writer`。桌面空闲不代表桌面已经释放聊天的写入所有权。

因此，不能把当前方案表述为“安装一个插件就已能通过手机双向操控桌面同一聊天”。需要先解决接入桌面同一运行实例的问题，再验证实时事件、继续任务、审批和桌面界面更新。

EasyTier 的打包、已有/内置双模式以及配置页面可以独立开发，不依赖解决上述聊天所有权问题。

### 两客户端临时实验

额外启动了一个仅监听回环地址的临时 app-server，两个本地 WebSocket 客户端均初始化成功。客户端 A 创建了仅驻留内存的临时聊天，客户端 B 的 `thread/loaded/list` 能看到同一聊天 ID。

但客户端 B 对该临时聊天调用 `thread/resume` 返回 `no rollout found for thread id ...`。这个临时聊天没有持久化 rollout，不能用这次实验声称已经验证完整的多客户端续聊。

临时服务已关闭，没有发送 `turn/start`，没有生成模型回答，也没有接入或重新配置桌面正在运行的服务。

## 对产品设计的影响

1. 历史列表和只读查看可以使用经过验证的接口。界面必须注明：来自持久化历史，不代表实时运行状态。
2. `thread/resume` 不能用来绕过另一个 app-server 的 writer lock。不能强制解锁、直接写数据库、写 rollout 或偷偷在别的进程里创建替代会话。
3. 要实现同一聊天双向操控，优先寻找并验证桌面提供的同实例连接/桥接机制。如果需要改桌面启动方式，先做隔离实验，不替换或修补用户安装的桌面程序。
4. 内置桌面工具能管理聊天，并不证明第三方插件后台拥有同样的外部调用接口，不能将本聊天里可用的内置工具直接当成插件 SDK。
5. 如果最终只能由我们自己的运行实例执行任务，应明确告诉用户其会话边界，不能把它称为官方桌面同一会话控制。

## 可复跑脚本

`scripts/verify-interfaces.mjs` 默认只读。`--resume-thread` 是显式的内存加载尝试，不发送任务，但可能初始化该聊天配置的集成。只对确定空闲的目标使用，不对运行中的当前聊天使用。

```powershell
$desktopBinary = Get-Process codex | Where-Object Path | Select-Object -First 1 -ExpandProperty Path
node scripts/verify-interfaces.mjs --codex $desktopBinary --easytier-cli 'C:\Program Files\easytier\easytier-cli.exe' --out '.local/verification/interface-results.local.json'
```

按需添加 `--read-thread <聊天ID>`、`--resume-thread <空闲聊天ID>`。`--schema <目录>` 可读取该版本 `app-server generate-json-schema --experimental` 生成的协议定义。

`scripts/verify-shared-runtime.mjs <桌面codex.exe路径> [结果文件]` 使用临时服务和临时聊天，验证结果包含上述临时聊天恢复限制，当前会以退出码 1 表示没有完成全部续聊检查。

机器相关结果保存在忽略的 `.local/verification/`；报告不保存聊天正文、网络密钥、节点完整配置或登录凭据。EasyTier `node` 的原始输出包含网络密钥，复跑脚本只输出字段白名单。
